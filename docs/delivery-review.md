# Delivery position review – read-only test step

`/delivery-preview.html` is a standalone, synthetic UI exercise. Its default case contains nine existing supplier products and one unknown position. A second case exercises duplicate supplier mappings, repeated receipt lines, missing conversion/price/number, different purchase units, changed descriptions and receipt-price changes. Edits invalidate the whole diagnostic result immediately; a superseded asynchronous response cannot restore it. There is no SDK, OCR, persistence, article creation or stock booking in this preview. The existing counting preview remains unchanged.

The shared `deliveryReview.js` classifies structured receipt positions. Names are only search suggestions. An exact supplier article number **and** purchase-unit code scoped to a supplier are needed for a `matched` diagnosis. Leading zeroes, punctuation and case in these identifiers are preserved. A single approved mapping additionally needs an active, unique outlet article, matching global product and base unit, versioned offer and positive conversion. Description differences are visible even with an exact number. Archived/draft duplicates are not silently ignored. Repeated article lines require review even if quantities or prices differ; genuine repeated receipt positions must later be explicitly handled, not silently deleted.

Every result says `requires_confirmation: true`, `bookable: false` and `writes_performed: false`. A suggestion score is never a product-identity proof. Numeric size/variant tokens survive name search normalization. The candidate list is bounded and reports truncation. Unknown versus suggested/ambiguous positions remain distinct. Unknown positions indicate the need for an admin-reviewed proposal; this step does not create one. Blank, zero, negative, excessive-precision and ambiguous quantities/prices remain explicit diagnostics. Free goods need a later documented confirmation path. Receipt price differences do not update an offer or article master price.

## Server boundary

`reviewDelivery` accepts only POST with the actual Base44 authentication, an authorized outlet and `X-Data-Env: dev`. Production calls are rejected. The request is bounded to 100,000 characters and 100 positions; client-supplied roles, approval flags, conversions and computed quantities are rejected. The function reads only: it has no mutation calls or booking dependency.

Catalog queries stop at 501 records rather than misrepresenting a truncated catalog. Only supplier mappings for products assigned at the authorized outlet are projected. A duplicate supplier identity referencing another product is flagged without disclosing that product's details. An unassigned product can therefore remain unknown at the employee review boundary; the future admin proposal approval must search the full authorized master catalog, including archived products, before any creation. This function does not replace that final duplicate check.

The read-only endpoint is also used by the connected delivery-draft workflow (see `delivery-drafts.md`). Actual Base44 draft operations and reloaded server diagnostics have been exercised with the admin account; employee sign-in remains untested. Local HTTP tests use in-memory entity adapters and do not establish actual platform permissions. No legacy write rules were relaxed or changed.

## Validation and next integration

16 additional automated tests cover matching, variants, duplicates, quantities, source prices, strict request shapes, actual-request identity checks, outlet scope, catalog limits and private-candidate projection. Together with the existing suite there are 82 tests. Both preview entries, full application build and targeted frontend lint are checked. Manual browser checks cover 9+1 results, an isolated unknown-position filter, conflict diagnostics and invalidation/recalculation after an input change.

The connected draft workflow now provides authenticated selectors, saved drafts with revision checks, persisted proposals and admin rejection/linkage to an existing approved product. Pending work: OCR ingestion as untrusted structured lines, creation/approval of truly new master products, complete canonical receipt deduplication, materializing immutable booking positions, resuming partial bookings through the stock journal, and history. Only after these parts and the actual employee/outlet test pass may the legacy write paths and permissions be cut over together. No production readiness is implied by this review-only step.
