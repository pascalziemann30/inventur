# Connected delivery drafts – test environment

`/InventoryCapture?workflow=delivery` connects the shared delivery review workspace to Base44. `DeliveryDraft` is a new aggregate with all direct client permissions denied. Source positions, versioned confirmations, embedded article proposals and request receipts are committed together through one conditional update. These embedded proposals are authoritative for this draft workflow; the older separate `ArticleProposal` entity is not also written or treated as a second queue.

## Scope

The actual Base44 user and outlet assignment are checked for reads and writes. Options expose only allowed active non-aggregator outlets and supplier id/name pairs. Catalog and draft queries stop at 501 rows. `deliveryDrafts` rejects production calls and client-supplied roles, computed quantities or approval metadata. All mutations require a current, bounded `INVENTORY_SESSION_TEST_ALLOWED` grant. Read-only options/list/get remain available after expiry; the UI disables changes on a read-only reload. The existing production write paths and their permissions are not changed.

The UI can start a delivery draft, list/reopen saved drafts, edit/add positions, explicitly save, confirm exact matches with warning acknowledgments, submit an unknown/uncertain position as an article proposal, and let the actual admin reject it or explicitly link it to an existing approved outlet offer. Notes and product/pack/quantity/price confirmation are required for manual admin linkage. A truly new product remains pending; this step does not create an active product or approve invented conversion factors. The original supplier description and number remain intact when an admin links an existing product; the effective mapping is stored separately in the confirmation.

Confirmed positions can now be explicitly selected and booked in the dev-only workflow. The server freezes their effective mapping and receipt price, books through the shared stock core with a stable operation id, and copies the durable stock receipt back into the draft. Unknown positions remain open for later proposal resolution. Booked source positions are immutable. No legacy `DeliveryLine` records are materialized. The separate photo/PDF scan now feeds these drafts after mandatory human review (see `delivery-scan.md`); new active master article approval and master-price changes remain outside this package.

## Concurrency and recovery

- A stable start key recovers uncertain draft creation. A provided reference is normalized conservatively with NFKC, trimming and case conversion, scoped by outlet and supplier. Existing references are rejected. Race-created duplicates are detected before mutations. Before any booking, a supplier/reference claim is conditionally appended to the existing outlet document. This atomic anchor prevents two drafts claiming the same reference. The outlet registry must be explicitly initialized; absent revision/registry fields reject booking. Claims stop at 1,000 rather than discard history. This does not provide file-hash/OCR or legacy cross-workflow deduplication.
- Each mutation includes an expected revision, unique request id and deterministic fingerprint. The request receipt and change share a conditional document write. Same-content retries acknowledge the prior write, including after a lost response; changed content under the same id is rejected. Another device's saved revision is never silently overwritten.
- The UI stores the exact request before sending it and retains uncertain requests for retry across reloads. Further changes are blocked until retry or explicit reload. Editing stores a local comparison copy. A conflict reload shows that copy separately from the server snapshot; it does not merge or overwrite it automatically.
- Editing a source position clears its confirmation. Its old proposal is retained in a bounded superseded history. Adding a repeated article line invalidates affected earlier confirmations. Effective mappings that point multiple positions at the same product produce a separate pre-booking review warning, including after a manual admin link. Such a warning is not a booking approval. Saved confirmations are rechecked against current approved offer revision, unit, conversion and outlet identity; changed configuration becomes visibly stale.
- Receipts stop at 1,000 requests and proposal history at 20 entries per position. Nothing is silently discarded to permit more writes. Removal of source positions is deliberately unsupported in this step.

## Frozen booking and recovery

A revision-checked selection enters `posting`. While posting, edits are blocked and retries must use the same selection. Each line uses `delivery-draft:<draft-id>:<line-id>` as its stock operation id. A committed stock write with a missing draft acknowledgment is recovered from the stock journal, without another increment. Successfully acknowledged lines display the before/after quantities and timestamp. The batch ends as `partially_booked` or `completed`. Effective same-product repeats block booking pending review; there is no override in this package. Each selected line requires exactly one linked stock record with matching identity and unit. Receipt prices remain frozen delivery evidence and never update master prices.

## Validation

20 additional tests exercise persisted drafts/proposals, lost-response recovery, competing edits, exact retries with reordered keys, duplicate start/reference races, actual user/outlet checks, confirmation invalidation, warning acknowledgment, proposal supersession, admin-only rejection/linkage, strict adapter results and test-only grants. The subsequent booking package adds 12 tests for partial and interrupted multi-position booking, repeat/concurrent requests, lost responses, failed acknowledgments, immutable frozen plans, repeated effective products and outlet-registry races. Together there are 114 automated tests. The fixture extension prepares only synthetic dev catalog data, four approved offers and two synthetic receipt positions; it does not book stock. Local builds and lint are run, and GitHub Actions checks the same suite. Runtime evidence is recorded separately in the local workspace after the actual Base44 exercise; these unit tests alone do not establish actual employee-login or platform integration success.

## Observed Base44 admin exercise on 2026-10-22

A separate synthetic outlet, supplier, four articles and four approved offers were created exclusively in Test Data. A two-line delivery draft was persisted. Editing the milk line to 3.25 cartons at a receipt price of 16 was retained through a full page reload; the server recomputed 32.5 litres and preserved the master price. After explicit warning acknowledgment its assignment was confirmed. The unknown line was proposed, survived reload, was rejected with an admin reason, proposed again, then manually linked to an existing approved synthetic article with an explicit product/pack/quantity/price check. No active master article was created and no stock booking function was called.

Two actual browser windows then held revisions 6 and 7. The first saved a quantity of 4; the second attempted 5 using its older revision and was rejected. Explicit reload retained 5 as a separate local comparison copy alongside the server's 4. These are real Base44 conditional updates, not just memory-adapter tests. The final effective-duplicate warning covers the manually linked synthetic line and its other same-product position. Actual employee sign-in and assignment remain untested; the runtime actor was the real admin.

After the grant expired, an attempted draft save was rejected and the authorized reload remained read-only at revision 7 with quantity 4. The rejected local quantity 6 remained a comparison copy. The separately gated fixture-inspection call returned HTTP 503. The feature setting was additionally returned to `disabled`. A read-only dashboard inspection independently showed the new synthetic stocks still at 10 litres milk, 24 cake pieces, 3.5 kg fruit and 12 paper rolls. The production OutletItem view was explicitly selected and contained zero records. Runtime screenshots and synthetic record identifiers stay in local evidence files rather than the public repository.


## Observed Base44 partial-booking exercise on 2026-10-22

A fresh synthetic test outlet was prepared with an initialized receipt registry and four stock records. The known milk position was confirmed at 2.5 cartons / 25 litres, while the unknown position was saved as a pending admin proposal. The explicit booking dialog listed +25 litres before submission. The actual booking locked the milk position and displayed a durable history receipt: stock 10 → 35 litres. The unknown proposal remained open and editable independently.

A second actual browser window still held the older revision 2. Repeating its original booking selection returned the current booked state without another increment. The independent gated stock inspection showed milk quantity 35, revision 1 and one journal entry; cake remained 24 pieces, fruit 3.5 kg and paper 12 rolls, all at revision 0 with no entries. A full reload retained the booked line, history and pending proposal. The runtime actor was the actual admin, not a genuine employee login. This exercise proves the new reference-claim and stock adapters in the Base44 dev runtime; it does not establish complete OCR/file duplicate detection or production cutover readiness.
